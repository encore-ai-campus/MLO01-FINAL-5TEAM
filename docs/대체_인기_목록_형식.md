# 대체 인기 목록 파일 형식

| 항목 | 내용 |
|---|---|
| 만드는 쪽 | 데이터(일 배치) |
| 쓰는 쪽 | 추천 API(대체 추천) |
| 둘 곳 | AWS S3. 첫 목록은 API 배포 이미지에도 넣는다 |
| 만드는 주기 | 재생 하루마다 한 번 |
| 쓰는 쪽이 새 목록을 찾는 주기 | 실제 시간 1분마다 |

## 1. 언제 쓰나

Redis나 PostgreSQL을 읽지 못하거나 추천 계산이 시간 안에 끝나지 않으면, 추천 API는 메모리에 올려 둔 이 목록으로 대신 응답한다(대체 추천). 저장소가 멈춰도 빈 목록 대신 인기 상품을 보여 주기 위해서다.

- 홈·목록 화면은 전체 순위를 쓴다.
- 상품 상세는 지금 보는 상품의 카테고리 순위를 쓰고, 모자라면 전체 순위로 채운다.
- 대체 추천으로 낸 카드의 노출 로그에는 `is_fallback = true`, `rec_model_version` = 이 목록의 버전, `feature_as_of_utc` = 이 목록의 집계 마감 시각을 남긴다(토픽 메시지 형식).

## 2. 순위를 매기는 규칙

| 규칙 | 내용 |
|---|---|
| 점수 | 집계 기간에 그 상품을 산 고유 사용자 수 |
| 집계 기간 | 집계 마감 시각 직전 7일. 시작 시각은 넣고 마감 시각은 넣지 않는다 |
| 기간의 기준 시각 | 구매 행동의 `event_time_utc`(재생 데이터 속 시각, UTC) |
| 정렬 | 점수 내림차순, 같으면 상품 ID를 숫자로 보아 오름차순 |
| 넣는 행동 | 재생 출처에서 판정을 통과한 구매만 |
| 개수 | 전체 200개, 카테고리마다 50개. 구매가 그보다 적으면 있는 만큼 |

- 예: 집계 마감 시각이 11-05 00:00이면 10-29 00:00 이상 11-05 00:00 미만의 구매를 센다.
- 화면·부하 시험 행동은 넣지 않는다. 사람 데이터는 집계에서 뺀다는 원칙과 같다.
- 점수와 정렬은 추천 모델이 후보를 보충할 때 쓰는 구매 인기 목록과 같은 정의다. 다만 추천 모델은 요청 시각 직전 7일로 계산하고, 이 목록은 하루 경계에서 고정한다.
- 가격이 없는 상품(가격이 비었거나 0)도 넣는다. 화면은 "가격 정보 없음"으로 보여 준다.

### 2.1 키 만드는 법

| 키 | 만드는 법 |
|---|---|
| 상품 ID | 숫자만으로 된 10진수 문자열(앞에 0을 붙이지 않음). 정렬은 숫자 값으로 한다 |
| 카테고리 키 | 구매 행의 카테고리 이름 → 없으면 카테고리 ID의 10진수 문자열 → 둘 다 없으면 `unknown` |

카테고리 키는 피처 계산과 같은 규칙이다. 상품 상세에서는 그 시점 상품 정보의 카테고리 이름과 ID로 같은 키를 만들어 찾는다.

## 3. 파일 구조

목록 한 벌은 JSON 파일 하나와 체크섬 파일 하나다.

| 필드 | 타입 | 뜻 |
|---|---|---|
| `format_version` | 정수 | 이 형식의 버전. 지금은 1 |
| `list_version` | 문자열 | 목록 버전(4장) |
| `replay_run_id` | 문자열 | 이 목록을 만든 재생 실행 ID. 첫 목록은 `base` |
| `data_cutoff_utc` | 문자열 | 집계 마감 시각(UTC) |
| `generated_at_utc` | 문자열 | 실제로 파일을 만든 시각(UTC) |
| `publish_request_id` | 문자열 | 이 목록을 만든 게시 요청 ID(4.1절). 일 배치는 `daily` |
| `window_days` | 정수 | 집계 기간(일). 지금은 7 |
| `overall` | 배열 | 전체 순위 |
| `by_category` | 객체 | 카테고리 키 → 그 카테고리 순위 |

순위의 한 칸은 `product_id`(문자열), `rank`(1부터), `buyer_count`(정수)다. 아래 예시는 일부만 보인다.

```json
{
  "format_version": 1,
  "list_version": "pop-20191105T000000Z-r1",
  "replay_run_id": "run-20261201-01",
  "data_cutoff_utc": "2019-11-05T00:00:00Z",
  "generated_at_utc": "2026-12-01T09:12:30Z",
  "publish_request_id": "daily",
  "window_days": 7,
  "overall": [
    {"product_id": "1004856", "rank": 1, "buyer_count": 812},
    {"product_id": "1005115", "rank": 2, "buyer_count": 640}
  ],
  "by_category": {
    "electronics.smartphone": [
      {"product_id": "1004856", "rank": 1, "buyer_count": 812}
    ],
    "unknown": [
      {"product_id": "5100816", "rank": 1, "buyer_count": 33}
    ]
  }
}
```

체크섬 파일 `popular.json.sha256`에는 JSON 파일 바이트 전체의 SHA-256 값(16진수 소문자 64자)만 담는다.

## 4. 버전, 저장 위치, 게시 순서

목록 버전은 `pop-` + 집계 마감 시각 + `-r` + 수정 번호다(예: `pop-20191105T000000Z-r1`). 처음 만들면 `r1`이고, 집계 오류를 고쳐 같은 마감 시각으로 다시 만들면 `r2`처럼 번호를 올린다. 이미 게시한 버전은 덮어쓰지 않으므로, 한 실행 안에서 버전 하나는 늘 같은 내용을 가리킨다.

| 경로(S3) | 내용 |
|---|---|
| `fallback/{replay_run_id}/{list_version}/popular.json` | 목록 |
| `fallback/{replay_run_id}/{list_version}/popular.json.sha256` | 체크섬 |
| `fallback/{replay_run_id}/manifest.json` | 그 실행의 버전 목록(버전, 집계 마감 시각, 경로, 체크섬, 다시 게시한 경우 게시 요청 ID) |

- 게시 순서는 목록 → 체크섬 → 버전 목록이다. 버전 목록에 오른 버전만 쓰므로, 중간에 멈춰도 반쯤 올라간 목록을 읽지 않는다.
- 게시는 한 번에 하나만 한다. 사람이 직접 돌리는 다시 게시도 일 배치와 동시에 돌리지 않는다.
- 목록과 체크섬은 같은 이름의 객체가 없을 때만 쓴다(S3 조건부 쓰기 `If-None-Match`). 버전 목록은 처음 만들 때는 없을 때만 쓰고, 그 뒤에는 읽은 버전이 그대로일 때만 바꾼다(`If-Match`).
- 게시 전에 목록이 6장의 본문 검사(형식 버전, 순위, 상품 ID, 빈 전체 순위)를 통과해야 한다. API가 버릴 목록을 게시하지 않기 위해서다.
- 같은 일 배치를 다시 돌렸는데 그 마감 시각의 버전이 이미 버전 목록에 있으면 게시를 건너뛴다.
- 목록 버전은 실행마다 `r1`부터 매기므로, 목록 하나는 실행 ID와 목록 버전을 함께 써야 가리킬 수 있다.
- `fallback/{replay_run_id}/` 아래 객체는 버린 번호까지 그 재생 실행이 끝날 때까지 지우지 않는다. 다음 번호를 셀 때 필요하기 때문이다. 게시 작업에는 이 경로의 목록 조회 권한을 준다.

### 4.1 멈춘 게시를 다시 돌릴 때

목록을 새로 만들지 않고 이미 올라간 파일로 이어서 게시한다. 목록에 생성 시각이 들어 있어 다시 만들면 같은 내용이 나온다고 보장할 수 없기 때문이다.

| 다시 돌릴 때 상태 | 처리 |
|---|---|
| 같은 요청이 남긴, 버전 목록에 없는 목록 파일이 있음 | 가장 큰 번호 하나를 확인한 뒤 버전 목록에 올린다 |
| 그 파일이 확인을 통과하지 못함 | 그 번호는 버리고 다음 번호로 새로 만든다 |
| 집계 오류를 고쳐 일부러 다시 게시 | 사람이 새 게시 요청 ID를 붙여 "다시 게시"로 돌린다. 건너뛰기 규칙은 적용하지 않는다 |

- 확인 항목: 6장의 본문 검사를 통과하고, 본문의 실행 ID·버전·집계 마감 시각이 이번 게시와 같아야 한다. 체크섬 파일이 없으면 목록 바이트로 만들어 쓰고, 있으면 그 값이 목록 바이트의 SHA-256과 같아야 한다.
- 시간 초과, 권한 오류, S3 서버 오류로 읽지 못한 것은 손상으로 보지 않는다. 번호를 버리지 않고 다시 시도한다.
- 다음 번호는 버전 목록과 S3에 있는 목록·체크섬 객체를 모두 보고, 가장 큰 번호에 1을 더한다. 번호는 숫자로 비교한다(`r10`이 `r9`보다 크다). 체크섬만 남은 번호도 쓴 번호로 센다.
- 게시 요청 ID는 그 실행 안에서 요청마다 새로 만들고, 같은 요청을 다시 돌릴 때는 같은 ID를 쓴다.
- 다시 게시는 먼저 버전 목록에서 같은 게시 요청 ID를 찾는다. 있으면 이미 끝난 것이라 멈춘다. 없으면 위 표대로 같은 요청의 파일을 이어서 게시하거나 다음 번호로 만든다. 그래서 응답을 못 받고 다시 돌려도 번호가 두 번 늘지 않는다.
- 본문의 게시 요청 ID가 다른 파일(앞선 일 배치나 다른 요청이 남긴 것)은 이어서 게시하지 않는다. 고치기 전의 목록이 수정본으로 오르는 것을 막기 위해서다.
- 버전 목록에 오르지 않은 파일은 API가 읽지 않는다. 버린 번호의 파일도 마찬가지다.
- 수정본은 그 마감 시각이 지금 고를 버전일 때만 API에 쓰인다. API가 이미 다음 날 목록을 쓰고 있으면 버전 목록에 올라도 바뀌지 않는다.

## 5. 만드는 시점

- 재생 시각이 하루 경계(UTC 00:00)를 넘으면, 밀린 처리가 끝난 뒤 도는 일 배치가 만든다. 집계 마감 시각은 그 하루 경계다.
- 입력은 그 실행의 Delta 정제 표를, 처리 완료를 확인한 뒤 고정한 버전으로 읽는다. 재생 첫 주처럼 집계 기간이 재생 시작 전으로 넘어가면 10월 원본의 구매를 함께 센다.
- 게시까지 마친 뒤 재생을 재개한다. 게시에 실패하면 경고를 남기고 재생을 그대로 재개한다. API는 전날 목록을 계속 쓰고, 일 배치는 다음 하루 경계 전까지 게시를 다시 시도한다. 전날 목록은 집계 마감 시각이 재생 시각보다 이르므로 아직 일어나지 않은 구매가 섞이지 않는다.
- 재개 뒤 최대 1분 동안은 아직 새 목록을 읽지 않은 API 파드가 전날 목록을 쓸 수 있다. 하루 차이의 인기 순위라 허용한다.
- 첫 목록(`base`)은 10월 데이터로 만들고 집계 마감 시각은 11-01 00:00이다. API 배포 이미지에 넣어, S3를 읽지 못해도 API가 뜰 수 있게 한다.

## 6. 쓰는 쪽 규칙

| 상황 | 동작 |
|---|---|
| 시작할 때 | 지금 재생 실행의 버전 목록에서 쓸 버전을 골라 올린다 |
| 시작할 때 S3를 못 읽음 | 배포 이미지의 `base`로 시작한다 |
| 쓸 버전 고르기 | 집계 마감 시각이 지금 재생 시각 이하인 것 중 가장 최근, 같은 마감 시각이면 수정 번호가 가장 큰 것 |
| 재생 시계가 없음(재생하지 않을 때) | 가장 최근 버전 |
| 재생 시계를 읽지 못함 | 새 버전으로 바꾸지 않고 쓰던 목록을 유지 |
| 갱신 | 1분마다 버전 목록을 다시 읽어, 고를 버전이 바뀌면 내려받아 바꾼다 |

내려받은 파일은 아래를 모두 통과해야 쓴다. 하나라도 어긋나면 버리고 쓰던 목록을 유지한다.
- SHA-256이 체크섬 파일과 버전 목록의 값 모두와 같다.
- `format_version`을 안다.
- 본문의 실행 ID·버전·집계 마감 시각이 버전 목록과 같다.
- 순위가 1부터 빠짐없이 이어지고, 상품 ID가 2.1절 형식이며, 전체 순위가 비어 있지 않다.

쓰던 목록이 다른 재생 실행의 것이거나 집계 마감 시각이 지금 재생 시각보다 늦으면 유지하지 않고 `base`로 바꾼다. 재생 시각보다 늦은 목록을 쓰지 않는 것은, 아직 일어나지 않은 구매로 만든 순위를 보여 주지 않기 위해서다.

새 재생 실행은 Redis 실시간 키를 비운 뒤 시작하므로(데이터 파이프라인 설계서 3.1절) Redis가 정상일 때만 시작된다. 그래서 Redis 장애 중에는 실행이 바뀌지 않고, API는 장애 전 실행의 목록을 그대로 써도 된다.

### 6.1 목록이 모자랄 때

- 상품 상세에서는 지금 보는 상품을 빼고 카테고리 순위를 쓰며, 모자라면 전체 순위로 채운다.
- 장바구니·구매한 상품은 알 수 있을 때만 뺀다. 저장소 장애 중에는 모를 수 있다.
- 전체 순위는 최대 200개라, 화면 한 줄의 카드 수보다 적어지는 일은 사실상 없다. 그래도 모자라면 있는 만큼만 보여 준다.
