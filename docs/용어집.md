"코드 이름"은 코드와 데이터에서 쓰는 이름이고, 규칙은 9장에 있다. "쓰지 않는 말"은 같은 대상을 다르게 부르던 말이다. 문서를 쓰거나 고칠 때 이 말이 보이면 "쓰는 말"로 바꾼다. 외부 문서의 제목과 인용, 업계 고유 용어(고객 데이터 플랫폼, 고객 사례 등), 용어 설명의 괄호 별칭은 바꾸지 않는다.

| 결정 목록 | decision log | — | 결정과 이유, 변경 이력을 적는 문서 | — |

## 9. 이름 규칙

코드와 데이터의 이름은 아래 규칙을 따른다. 토픽별 필드 목록은 "행동·노출·클릭 토픽 메시지 형식" 문서가 정하고, 이름이 이 장과 다르면 이 장을 따른다. "새로 정함"은 이 장에서 처음 정한 이름이다.

### 9.1 공통 규칙

아래 표기 규칙은 토픽, 필드, 컬럼, 표, 지표, 모델 이름과 MLflow 별칭·태그에 쓴다. Redis 키(9.5절)와 버전 값(예: `rec-2026.12.01-1`)은 각자의 형식을 따른다.

| 대상 | 규칙 | 예 |
|---|---|---|
| 표기 | 영어 소문자와 밑줄(`snake_case`) | `replay_run_id` |
| 식별자 | `_id`로 끝냄 | `event_id`, `session_id` |
| 시각 | UTC로 쓰고 `_utc`로 끝냄. 사건 시각은 `_time_utc`, 생성·처리 시각은 `_at_utc` | `event_time_utc`, `produced_at_utc` |
| 기간 | 데이터 필드는 `_ms`(새로 정함), 모니터링 지표는 `_seconds` | `lag_ms` |
| 참·거짓 | `is_`로 시작 | `is_fallback` |
| 버전 | `_version`으로 끝냄 | `schema_version`, `rec_model_version` |
| 약어 | `id`, `utc`, `ms`, `rec`(추천), `covisit`(함께 본 상품), `ttl`, `sha256`만 씀(새로 정함) | — |
| 원본 컬럼 | 원본 데이터셋의 컬럼은 이름을 바꾸지 않음(위 규칙의 예외) | `event_time`, `user_session` |

값의 형식:
- Kafka 메시지(JSON)의 ID는 숫자로 보이더라도 문자열로 보낸다. 브라우저가 큰 정수를 숫자로 읽으면 끝자리가 바뀌기 때문이다. 값이 없는 필드는 빼지 않고 `null`로 둔다.
- 원본 Parquet은 원본 타입을 그대로 둔다(사용자·상품·카테고리 ID는 64비트 정수, 원본 세션 ID는 문자열). Kafka 메시지를 쌓은 Delta 표는 메시지와 같이 ID를 문자열로 둔다(새로 정함). 두 데이터를 이을 때는 ID를 문자열로 맞춘다.

### 9.2 Kafka 토픽

| 토픽 | 이름 | 비고 |
|---|---|---|
| 행동 토픽 | `behavior` | 메시지 형식 문서 |
| 정제 토픽 | `behavior_clean` | 새로 정함 |
| 피드백 토픽 | `feedback` | 메시지 형식 문서 |
| 예측 요청 토픽 | `conversion_request` | 메시지 형식 문서 |

- 토픽 이름은 소문자와 밑줄만 쓴다(Kafka는 마침표·하이픈도 허용). Kafka는 내부 지표 이름에서 마침표를 밑줄로 바꿔 다루므로 `behavior.clean`과 `behavior_clean`은 충돌한다. 밑줄만 쓰면 이런 충돌이 생기지 않는다.
- 토픽 이름에 환경(로컬·AWS)을 넣지 않는다. 환경은 클러스터로 나뉜다.

### 9.3 원본 컬럼

원본 데이터셋의 컬럼이다. 원본 Parquet에서 이름을 그대로 쓴다. Kafka 메시지와 이를 쌓은 Delta 표는 9.4절의 필드 이름을 쓴다(예: `event_time` 값은 `event_time_utc`로 보냄).

| 컬럼 | 뜻 |
|---|---|
| `event_time` | 행동 발생 시각(UTC) |
| `event_type` | 행동 종류 |
| `product_id` | 상품 ID |
| `category_id` | 카테고리 ID |
| `category_code` | 카테고리 이름 |
| `brand` | 브랜드 |
| `price` | 가격 |
| `user_id` | 사용자 ID |
| `user_session` | 원본 세션 ID |

### 9.4 팀이 붙이는 필드·컬럼

| 이름 | 뜻 | 쓰는 곳 |
|---|---|---|
| `event_id` | 이벤트 ID. 재생은 `원본 파일명:행 순번` | 원본 Parquet, 메시지, Delta |
| `source_file` | 원본 파일명 | 원본 Parquet, 메시지 |
| `source_row` | 원본 파일의 행 순번(0부터) | 원본 Parquet, 메시지 |
| `source` | 출처: `replay`, `web`, `loadtest`(피드백은 `test` 추가) | 메시지, Delta |
| `replay_run_id` | 재생 실행 ID | 메시지, Delta, Redis 시계 키 |
| `schema_version` | 메시지 형식 버전 | 메시지 |
| `sequence` | 같은 `raw_session_id` 안의 순서 | 메시지 |
| `raw_session_id` | 생산자가 보낸 세션 값(아래) | 메시지, Delta 원본 표 |
| `session_id` | 세션 ID(30분 규칙) | 정제 토픽, Delta 정제 표, Redis, 피드백 학습 데이터 |
| `event_time_utc`, `replay_time_utc`, `produced_at_utc` | 행동 시각, 재생 시각, 메시지 생성 시각 | 메시지 |
| `log_id`, `log_type` | 피드백 기록 ID와 종류 | 피드백 메시지 |
| `request_id`, `impression_id`, `prediction_id` | 추천 응답, 노출, 구매 전환 예측의 ID | 피드백 메시지 |

- `raw_session_id`는 재생이면 원본 세션 ID, 화면이면 `web-`를 붙인 분석용 세션 ID, 부하 시험이면 `load-`로 시작하는 값이다. `session_id`는 이 값이 아니라 출처·재생 실행과 메시지 키가 같은 행동의 무활동 30분 규칙으로 판정 작업이 만든다(데이터 파이프라인 설계서 4장). 값은 그 세션의 첫 통과 행동의 이벤트 ID이고, 늦음·중복 판정을 받은 행동은 세션을 시작하거나 늘이지 않는다.
- `session_id`는 30분 규칙의 세션 ID에만 쓴다. 화면·부하 시험은 브라우저마다 메시지 키가 달라, 같은 계정이라도 브라우저가 다르면 `session_id`가 따로다.
- 행동 토픽과 정제 토픽의 메시지 키는 재생이면 사용자 ID, 화면·부하 시험이면 로그인 여부와 상관없이 `raw_session_id`다. 세션 도중 로그인해도 키가 바뀌지 않아 같은 세션이 이어진다(데이터 파이프라인 설계서 4장).
- 로그인한 사용자의 화면 행동 `user_id`는 `web-` + 화면 서버 계정 ID다(예: `web-17`). 재생 데이터의 숫자 사용자 ID와 겹치지 않는다.

### 9.5 Redis 키

형식은 `분류:대상[:v정의 버전]:ID[:세부]`이다. 콜론으로 나누고 소문자로 쓴다. 키 목록과 쓰는 작업은 데이터 파이프라인 설계서 3.4절에 있다.

| 키 | 뜻 |
|---|---|
| `clock:{재생 실행 ID}` | 재생 시계 |
| `feat:session:{세션 ID}`, `feat:session:{세션 ID}:recent` | 실시간 세션 피처, 최근 본 상품 |
| `feat:current_session:{메시지 키}` | 현재 세션 기록(새로 정함) |
| `feat:user:{사용자 ID}:purchased` | 사용자 구매 이력(실시간) |
| `feat:user:v{정의 버전}:{사용자 ID}`, `feat:item:v{정의 버전}:{상품 ID}` | 배치 피처 |
| `feat:covisit:v{정의 버전}:{상품 ID}` | 관계표 |

- 배치 피처는 정의 버전을 키에 넣고, 실시간 피처는 넣지 않는다(실시간 정의는 한 재생 실행 동안 고정).
- Feast를 쓰면 배치 피처 키는 Feast의 저장 형식을 따른다.

### 9.6 Delta 표

이름은 원천 토픽 이름 뒤에 계층을 붙인다(새로 정함). 표 이름에는 버전을 넣지 않는다. 피처 정의 버전과 리비전은 컬럼으로 두고, 학습 데이터의 시점 고정은 Delta 표 버전으로 한다.

| 표 | 이름 |
|---|---|
| 원본 표(행동 토픽 그대로) | `behavior_raw` |
| 정제 표 | `behavior_clean` |
| 실시간 피처 이력 | `feature_history` |
| 피드백 적재본 | `feedback_raw` |

표마다 열은 아래와 같다(새로 정함). ID는 문자열, 시각은 UTC 시각 타입으로 둔다. 사용자·상품 배치 피처를 담는 표는 Feast 사용 여부를 정한 뒤 정한다.

| 표 | 열 |
|---|---|
| `behavior_raw` | 행동 토픽 메시지의 모든 필드(같은 이름) + `behavior_partition`, `behavior_offset`, `ingested_at_utc` |
| `behavior_clean` | 정제 토픽 메시지의 모든 필드(아래) + `clean_partition`, `clean_offset`, `ingested_at_utc` |
| `feature_history` | 키 열, 위치 열, 세션 피처 값 열(아래) |
| `feedback_raw` | 피드백 토픽 메시지의 모든 필드(같은 이름) + `feedback_partition`, `feedback_offset`, `ingested_at_utc` |

- 위치 열은 그 행을 읽은 Kafka 토픽의 파티션과 오프셋이다. `behavior_`는 행동 토픽, `clean_`은 정제 토픽, `feedback_`은 피드백 토픽의 위치다. `ingested_at_utc`는 Delta에 쓴 실제 시각이다.
- 정제 토픽 메시지는 행동 토픽 메시지의 모든 필드에 `behavior_partition`, `behavior_offset`, `session_id`와 판정 결과 필드(아래)를 더한 것이다.

| 판정 결과 필드 | 형식 | 뜻 |
|---|---|---|
| `judge_result` | 문자열 | `passed`(통과), `late`(늦음), `duplicate`(중복), `schema_error`(형식 오류) |
| `judge_run_id` | 문자열 | 판정 작업 실행 ID |
| `judge_batch_number` | 정수 | 판정 배치 번호 |
| `judged_replay_time_utc` | 시각 | 판정 배치의 처리 재생 시각. 다시 실행해도 같은 값(데이터 파이프라인 설계서 4장) |

`feature_history`는 판정을 통과한 이벤트마다 한 행(그 이벤트를 반영한 직후의 세션 상태)을 남긴다.

| 묶음 | 열 |
|---|---|
| 키 | `replay_run_id`, `session_id`, `feature_version`(피처 정의 버전), `feature_revision`(피처 리비전) |
| 위치·행동 | `behavior_partition`, `behavior_offset`, `event_id`, `event_time_utc`, `user_id` |
| 최근 목록 | `recent_products`(최근 본 상품 20개: 상품 ID·시각·체류 시간), `recent_actions`(최근 조회·장바구니 담기 5개) |
| 개수·시간 | `view_count`, `cart_count`, `repeat_view_count`, `category_count`, `elapsed_ms` |
| 분포 | `category_ids`, `price_bands`, `dwell_mean_ms`, `dwell_max_ms` |
| 시각 | `hour_of_day`, `day_of_week` |

- 피처 값 열의 계산 규칙은 데이터 파이프라인 설계서 3.3절을 따른다. 피처를 더하거나 빼거나 계산 규칙을 바꾸면 `feature_version`을 올린다.
- 다음 행을 이어 계산하는 데 필요한 중간 상태(예: 세션에서 본 상품 집합, 체류 시간 합)는 데이터 담당이 열로 더한다. 최근 20개 목록만으로는 오래전에 본 상품의 재조회를 셀 수 없기 때문이다.
- 피드백 로그는 `replay_run_id`와 `feature_revision`으로 이 표의 행을 찾는다. 리비전은 행동 토픽 위치라 한 이벤트만 가리킨다. 정의 버전이 둘 이상이면 모델의 `feature_version` 태그(9.8절)로 고른다.
- 실시간 피처의 기준 시각은 그 행의 `event_time_utc`다. Redis에 실제로 들어간 시각(사용 가능 시각)은 이 표에 없다. 서빙 로그가 있는 구간은 로그의 리비전으로 피처를 붙이므로 필요 없다.
- 처리 위치와 사용자 구매 이력은 이 표에 두지 않고 `behavior_clean`에서 다시 계산한다.
- `recent_actions`의 원소 형식은 "최근 행동 목록 형식" 문서를 따른다.

### 9.7 모니터링 지표(Prometheus)

Prometheus 공식 이름 권고를 따르고, 순서는 팀 규칙으로 정한다.
- 형식은 `구성 요소_측정 대상_단위`이다(팀 규칙, 예: `replayer_events_sent_total`).
- 단위는 기본 단위(초, 바이트)로 쓰고 이름에 붙인다(`_seconds`, `_bytes`). 누적값(카운터)은 끝에 `_total`을 붙인다(예: `cpu_seconds_total`). 0~1 비율은 `_ratio`를 쓴다(팀 규칙).
- 사용자 ID, 세션 ID처럼 값의 종류가 많은 것은 레이블로 쓰지 않는다. 레이블 조합마다 시계열이 따로 생겨 메모리가 늘기 때문이다.

### 9.8 MLflow 모델

| 대상 | 등록 모델 이름 | 배포 버전 표시 |
|---|---|---|
| 추천 모델 | `rec_model`(새로 정함) | `rec-날짜-순번`(예: `rec-2026.12.01-1`) |
| 구매 전환 예측 모델 | `conversion_model`(새로 정함) | `conversion-날짜-순번`(새로 정함) |

- 배포 버전 표시는 MLflow가 매기는 버전 번호와 별개로, 그 버전에 태그로 붙이고 메시지의 모델 버전 필드에 쓰는 값이다.

MLflow 안에서 운영 모델은 별칭으로 가리킨다(새로 정함). 별칭은 한 등록 모델 안에서 한 버전에만 붙는다.

| 별칭 | 뜻 |
|---|---|
| `production` | 지금 서빙하는 버전 |
| `candidate` | 재학습 뒤 판정을 기다리는 버전. 후보는 한 번에 하나만 둔다 |

| 태그 | 값 |
|---|---|
| `deploy_version` | 배포 버전 표시(예: `rec-2026.12.01-1`) |
| `feature_version` | 학습에 쓴 피처 정의 버전 |
| `train_data_version` | 학습 데이터 버전 |
| `train_cutoff_time_utc` | 학습 데이터에 넣은 마지막 행동의 시각(원본 기준) |
| `code_version` | 학습 코드의 git 커밋 |

- 학습에 쓴 입력 표와 표마다의 Delta 버전, 추천 모델의 관계표 버전은 학습 데이터 명세 파일로 그 학습 실행에 함께 남긴다.
- 배포 순서: S3에 모델 묶음 올리기 → (추천만) 관계표 적재와 준비 완료 확인 → S3 현재 버전 정보 갱신 → `production` 별칭 옮기기. 되돌리기도 같은 순서로 이전 버전을 다시 가리킨다.
- S3 갱신이 실패하면 이전 버전을 그대로 쓰고 별칭은 옮기지 않는다. 별칭과 S3가 어긋나면 S3에 맞춘다.
- 추천·구매 전환 예측 API는 MLflow를 직접 읽지 않고 S3의 현재 버전 정보를 읽는다. MLflow가 있는 노트북이 꺼져도 API가 다시 뜰 수 있게 하기 위해서다. 현재 버전 정보의 형식은 모델 묶음 형식과 함께 ML 담당이 정한다.
- 배포가 끝난 뒤에는 현재 버전 정보의 버전 값과 `production` 별칭이 가리키는 버전의 `deploy_version`이 같다.
