# 행동·노출·클릭 토픽 메시지 형식

| 항목 | 내용 |
|---|---|
| 작성 | PM 이여찬 |
| 기준일 | 2026-11-26 |
| 스키마 버전 | 1 |

## 1. 정한 것

재생기·화면 서버·Redis 반영 작업이 Kafka에 보내는 메시지의 형식이다. 데이터 담당(재생기, 판정·적재 작업)과 서비스 담당(화면 서버, API)은 이 형식만 맞추면 따로 개발해도 맞물린다.

| 토픽 | 보내는 쪽 | 받는 쪽 | 메시지 키 |
|---|---|---|---|
| 행동 토픽 `behavior` | 재생기, 화면 서버, 부하 시험 도구 | 판정 작업, Delta 적재 작업 | 재생은 `user_id`, 화면·부하 시험은 `raw_session_id` |
| 피드백 토픽 `feedback` | 화면 서버, 추천·구매 전환 예측 API | 피드백 적재 작업 | 행동 토픽과 같음 |
| 예측 요청 토픽 `conversion_request` | Redis 반영 작업 | 예측 요청 처리 작업 | 행동 토픽과 같음 |

- 형식은 UTF-8 JSON 객체 한 개다. 모든 메시지에 `schema_version`을 넣는다.
- 판정 작업이 만드는 정제 토픽(`behavior_clean`)의 형식은 데이터 파이프라인 설계서 4장을 따른다. 이 문서는 정제 토픽에 들어가기 전 원래 메시지만 다룬다.
- 필드 이름은 영어 소문자와 밑줄로 쓴다. 시각 필드는 이름 끝에 `_utc`를 붙인다. 값이 없는 필드는 빼지 않고 `null`로 둔다.
- ID는 숫자로 보이더라도 문자열로 보낸다. 카테고리 ID처럼 큰 정수는 브라우저(JavaScript)에서 숫자로 읽으면 끝자리가 바뀐다.

## 2. 보내는 규칙

모든 생산자는 Kafka가 받았다고 확인한 뒤에만 성공으로 처리한다. AWS에서는 복제본 2곳 이상에 기록돼야 확인이 오도록(`acks=all`) 보낸다. 확인이 오지 않으면 같은 ID로 다시 보낸다. 판정 작업과 적재 작업은 같은 ID를 한 번만 반영한다.

| 생산자 | 다시 보낼 때 같은 값으로 두는 것 |
|---|---|
| 재생기 | 원본 행에서 정해지는 `event_id` |
| 화면 | 브라우저가 행동마다 만든 `event_id`·`sequence`, 노출·클릭마다 만든 `log_id` |
| 추천·구매 전환 예측 API | `log_id`(예측은 `prediction_id`와 같은 값) |
| Redis 반영 작업 | 기준 행동의 `source`·`replay_run_id`·`event_id` |

- 화면은 행동을 하나씩 순서대로 보낸다. 앞 행동의 전송 확인을 받은 뒤 다음 행동을 보내, 화면 서버가 여러 대여도 한 세션의 행동이 Kafka에 순서대로 들어간다.
- 중복 판정은 한 재생 실행 안에서, 판정 작업의 허용 지연 범위 안에서만 보장한다. 새 재생 실행은 상태를 처음부터 다시 쌓으므로, 같은 원본 행이 새 실행에서 다시 나오는 것은 중복이 아니다.
- 화면을 닫거나 다른 페이지로 옮기면 아직 보내지 못한 노출·클릭은 잃을 수 있다. 화면 기록은 화면이 열려 있는 동안만 다시 보낸다.

## 3. 시각 규칙

| 필드 | 뜻 | 형식 |
|---|---|---|
| `event_time_utc` | 행동이 일어난 시각. 재생은 원본 기록의 시각, 화면·부하 시험은 받은 순간의 재생 시각 | UTC, ISO 8601, 밀리초까지(`2019-11-01T00:00:03.000Z`) |
| `replay_time_utc` | 메시지를 만든 순간의 재생 시계 값 | 같음 |
| `produced_at_utc` | 메시지를 만든 실제 시각. 생산자 안의 지연을 볼 때 쓴다 | 같음 |

재생 시계는 재생기가 Redis의 시계 키에 쓰는 재생 실행 ID와 재생 시각이다. 화면 서버와 부하 시험 도구는 메시지를 만들 때마다 이 키를 읽어 `replay_run_id`, `event_time_utc`, `replay_time_utc`를 찍는다.

- 재생이 일시정지 중이면 시계 키의 마지막 재생 시각을 그대로 쓴다. 일 배치를 기다리는 동안에도 화면 행동이 2019년 시각 사이에 들어간다.
- 재생 실행이 없으면(시계 키가 없으면) 두 시각 모두 실제 시각을 쓰고 `replay_run_id`는 `null`이다.
- 반영 지연의 시작점인 "Kafka가 받아들인 시각"은 메시지 필드가 아니라 Kafka 레코드 시각으로 잰다. 이를 위해 행동·피드백·예측 요청 토픽은 브로커가 기록한 시각을 레코드 시각으로 쓰게 설정한다(`message.timestamp.type=LogAppendTime`).

## 4. 행동 토픽

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `schema_version` | 문자열 | 예 | `"1"` |
| `event_id` | 문자열 | 예 | 중복 판정 키. 출처별 규칙은 아래 표 |
| `source` | 문자열 | 예 | `replay`(재생), `web`(화면의 사람 행동), `loadtest`(부하 시험) |
| `replay_run_id` | 문자열 | 재생만 | 재생 실행 ID. 화면·부하 시험은 3장 규칙 |
| `event_type` | 문자열 | 예 | `view`(조회), `cart`(장바구니 담기), `purchase`(구매) |
| `event_time_utc` | 시각 | 예 | 3장 |
| `replay_time_utc` | 시각 | 예 | 3장 |
| `produced_at_utc` | 시각 | 예 | 3장 |
| `sequence` | 정수 | 예 | 같은 `raw_session_id` 안의 순서. 출처별 규칙은 아래 표 |
| `source_file` | 문자열 | 재생만 | 원본 파일 이름 |
| `source_row` | 정수 | 재생만 | 원본 파일의 0부터 시작하는 행 순번 |
| `user_id` | 문자열 | 아니오 | 사용자 ID. 로그인하지 않은 사용자는 `null` |
| `raw_session_id` | 문자열 | 아니오 | 생산자가 보낸 세션 값. 재생은 원본 세션 ID, 화면·부하 시험은 아래 표의 값 |
| `product_id` | 문자열 | 예 | 상품 ID |
| `category_id` | 문자열 | 예 | 카테고리 ID |
| `category_code` | 문자열 | 아니오 | 카테고리 이름(예: `electronics.smartphone`) |
| `brand` | 문자열 | 아니오 | 브랜드 |
| `price` | 실수 | 예 | 가격. 원본 값 그대로이며 통화 단위는 붙이지 않는다 |

- `event_type`에 세 값 외의 값이 오면 판정 작업이 스키마 오류로 표시한다. 재생기는 원본 값을 바꾸지 않고 보낸다.
- 원본 세션 ID는 빈 행과 여러 사용자가 함께 쓰는 값이 있어 세션 구분에 쓰지 않는다. 세션(행동 간격 30분 규칙)은 판정 작업이 출처·재생 실행과 메시지 키가 같은 행동을 이벤트 시각으로 나눠 만들고, 세션 ID는 그 세션의 첫 통과 행동의 이벤트 ID로 한다. 늦음·중복 판정을 받은 행동은 세션을 시작하거나 늘이지 않는다. 재생은 원본 세션 ID를 `raw_session_id`에 그대로 싣고, 빈 값은 `null`로 보낸다. 화면·부하 시험은 `raw_session_id`를 항상 채운다. 30분 규칙의 세션 ID(`session_id`)는 이 메시지에 없고 정제 토픽부터 붙는다.
- 화면의 `sequence`는 같은 `raw_session_id` 안의 순서만 정한다. 같은 사용자의 서로 다른 브라우저 사이 순서는 이벤트 시각으로 정하고, 같으면 원본 위치(행동 토픽 위치)로 정한다.

출처별 ID 규칙:

| 출처 | `event_id` | `sequence` | `user_id` | `raw_session_id` |
|---|---|---|---|---|
| 재생 | `원본 파일명:행 순번`(예: `2019-Nov.csv.gz:15`) | 원본 행 순번 | 원본 사용자 ID | 원본 세션 ID |
| 화면 | `web:` + 브라우저가 만든 UUID | 브라우저가 1부터 매기는 번호 | 로그인하지 않은 사용자는 `null`. 로그인한 사용자는 `web-` + 화면 서버 계정 ID(예: `web-17`) | `web-` + `web_session_id` |
| 부하 시험 | `load:` + 시험 실행 ID + `:` + 생성 순번 | 생성 순번 | 시험용 가짜 ID(`load-` 표식) | `load-` + 시험 실행 ID + 세션 번호 |

화면의 분석용 세션 ID(`web_session_id`)는 화면 서버가 사용자가 처음 접속할 때 따로 발급해 브라우저에 저장하는 값이다. 인증 세션의 키는 로그인할 때 바뀌므로 쓰지 않는다. 화면·부하 시험 행동은 로그인 여부와 상관없이 `raw_session_id`를 메시지 키로 쓴다. 세션 도중 로그인해도 키와 파티션이 그대로라 로그인 전후 행동이 순서대로 한 세션에 이어진다. 같은 계정이라도 브라우저가 다르면 세션이 따로다.

## 5. 피드백 토픽: 노출, 클릭, 예측

피드백 토픽에는 노출, 클릭, 예측 세 종류가 들어가고 `log_type`으로 구분한다. 노출과 클릭은 카드(쇼핑 화면에서 추천 상품 하나를 사진·이름·가격과 함께 보여 주는 칸) 단위로 센다. 예측 기록의 내용 필드는 구매 전환 예측 담당과 서비스 담당이 합의한 예측 기록 형식을 따르고, 공통 필드는 아래 표를 따른다.

공통 필드:

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `schema_version` | 문자열 | 예 | `"1"` |
| `log_id` | 문자열 | 예 | 중복 제거 키. 다시 보내도 같은 값 |
| `log_type` | 문자열 | 예 | `impression`(노출), `click`(클릭), `prediction`(예측) |
| `request_id` | 문자열 | 노출·클릭 | 한 추천 응답에서 나온 노출·클릭을 잇는다 |
| `source` | 문자열 | 예 | 행동 토픽의 세 값과 `test`(토픽을 거치지 않는 독립 시험). `test`는 예측에만 쓴다 |
| `replay_run_id` | 문자열 | 아니오 | 3장 규칙 |
| `event_time_utc`, `replay_time_utc`, `produced_at_utc` | 시각 | 예 | 3장 |
| `user_id` | 문자열 | 아니오 | 행동 토픽과 같은 규칙 |
| `raw_session_id` | 문자열 | 예 | 행동 토픽과 같은 규칙 |

예측 기록의 공통 필드:
- `log_id`는 `prediction_id`와 같은 값이다.
- 구매 전환 예측은 추천 요청이 아니라 예측 요청(6장)마다 계산하므로 `request_id`는 `null`이다. 예측과 추천 노출은 노출의 `prediction_id`로 잇는다.
- 예측 기록의 세션은 30분 규칙의 세션 ID(`session_id`)로 적는다. 공통 필드의 `raw_session_id`와 다르며 서로 대신할 수 없다.
- 예측 기록의 `feature_revision`은 예측 요청에 실린 값을 해석하지 않고 그대로 쓴다.

노출과 클릭에만 있는 필드:

| 필드 | 노출 | 클릭 | 설명 |
|---|---|---|---|
| `impression_id` | 예 | 예 | 노출 ID. 노출에서는 `log_id`와 같은 값. 클릭은 눌린 카드의 노출 ID |
| `prediction_id` | 아니오 | 아니오 | 이 응답과 함께 보인 구매 전환 예측의 ID. 없으면 `null` |
| `product_id` | 예 | 예 | 보이거나 눌린 상품 |
| `position` | 예 | 예 | 목록에서의 위치. 1부터 |
| `rec_model_version` | 예 | 아니오 | 추천 모델 버전. 대체 추천이면 인기 목록의 버전 |
| `is_fallback` | 예 | 아니오 | 대체 추천(인기 목록)으로 낸 카드면 `true` |
| `feature_revision` | 아니오 | 아니오 | API가 읽은 실시간 피처 리비전(뜻은 데이터 파이프라인 설계서 3.2절). 받은 값을 해석하지 않고 그대로 넣는다. 읽지 않았으면 `null` |
| `feature_as_of_utc` | 예 | 아니오 | 배치 피처 기준 시각. 대체 추천이면 인기 목록의 집계 기준 시각 |

- 노출은 한 추천 응답 안에서 카드가 처음 화면에 보일 때 카드마다 한 건 보낸다. 같은 응답의 카드가 스크롤로 다시 보여도 새 노출을 만들지 않는다. 카드 5장을 받아 2장이 보였으면 노출은 2건이다.
- 클릭이 노출보다 먼저 적재되더라도 적재 작업은 `impression_id`로 나중에 잇는다.
- 클릭 메시지에서 클릭에 없는 필드는 `null`이다.

## 6. 예측 요청 토픽

Redis 반영 작업은 구매 전환 예측 대상 행동을 Redis에 반영한 직후, 그 행동까지만 반영한 입력을 담은 예측 요청을 이 토픽에 쓴다. 예측 요청 처리 작업이 토픽을 읽어 구매 전환 예측 API를 부른다. Redis 반영 작업은 API를 기다리지 않고, API는 예측을 계산·저장할 때 Redis를 읽지 않는다.

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `schema_version` | 문자열 | 예 | `"1"` |
| `source`, `replay_run_id` | 문자열 | 4장 | 기준 행동의 값 |
| `event_id`, `event_type`, `sequence` | 4장 | 예 | 기준 행동(예측을 부른 행동)의 값 |
| `event_time_utc`, `replay_time_utc` | 시각 | 예 | 기준 행동의 값 |
| `user_id`, `raw_session_id` | 문자열 | 4장 | 기준 행동의 값 |
| `session_id` | 문자열 | 예 | 기준 행동이 속한 세션 ID |
| `session_status` | 문자열 | 예 | 요청을 만든 순간의 세션 상태(구매 여부 포함). 예측 기록 표(DB 설계)의 세션 상태 열에 같은 값으로 저장된다 |
| `input_event_id`, `input_time_utc` | 문자열, 시각 | 예 | 입력에 들어간 마지막 행동과 그 시각. 늘 기준 행동이다 |
| `input_version` | 문자열 | 예 | 입력 계산 규칙 버전 |
| `inputs` | 객체 | 예 | 입력 6개. 항목 이름과 자료형은 구매 전환 예측의 입력 계산 함수(학습과 실서비스 공용)를 따른다 |
| `feature_revision` | 문자열 | 예 | 기준 행동을 반영한 직후의 피처 리비전. 예측 기록에 그대로 남는다 |
| `produced_at_utc` | 시각 | 예 | Redis 반영 작업이 요청을 만든 실제 시각 |

- 예측 대상: 판정을 통과한 조회·장바구니 행동 중 화면·부하 시험 행동 전부와, 재생 행동 중 예측 시점으로 정한 행동. 재생의 예측 시점 규칙은 PM이 정한다.
- 메시지 키는 기준 행동의 메시지 키(4장)다. 한 세션의 요청이 한 파티션에 순서대로 들어간다. 레코드 시각은 다른 토픽처럼 브로커가 기록한 시각으로 둔다(3장).
- 같은 배치에 한 세션의 행동이 여럿이면 행동 하나씩 반영한 중간 상태에서 각 행동의 입력을 뗀다.
- Redis 반영 작업은 배치를 끝냈다고 기록하기 전에 그 배치의 요청을 쓴다. 배치를 다시 처리해 같은 요청이 두 번 가도 출처·재생 실행 ID·이벤트 ID가 같아 예측은 한 건만 남는다.
- 예측 요청 처리 작업은 API 호출을 마친 뒤 읽은 위치를 기록한다. 멈췄다 다시 돌아도 요청이 빠지지 않는다. 처리가 밀린 정도는 이 토픽의 소비 밀림으로 본다.
- 처리 작업이 늦게 읽거나 API가 느리면 요청이 토픽에 쌓일 뿐, Redis 반영과 추천 반영은 늦어지지 않는다. 다만 토픽 쓰기 자체가 막히면(Kafka 확인이 오지 않으면) 그 배치를 끝냈다는 기록이 늦어져 다음 배치의 Redis 반영도 늦어진다.

## 7. 형식을 바꿀 때

- 형식을 바꿀 때는 `schema_version`을 올리고, 받는 쪽은 한동안 이전 버전도 읽는다.
- 한 재생 실행 동안에는 토픽의 파티션 수와 메시지 키 규칙을 바꾸지 않는다. 한 세션의 행동 순서가 깨지기 때문이다.

## 부록 A. 쓰는 곳별로 필요한 값

메시지는 Kafka를 지나간 뒤에는 값을 덧붙일 수 없다. 아래 표는 메시지를 읽는 쪽마다 하는 일과 그 일에 필요한 필드다. 각 담당은 자기 행의 필드로 충분한지 확인한다.

| 쓰는 곳 | 하는 일 | 필요한 필드 |
|---|---|---|
| 판정 작업 | 중복 거르기, 늦은 행동 표시, 순서 맞추기 | `event_id`, `event_time_utc`, `sequence`, `raw_session_id`, `replay_run_id`, `schema_version` |
| 판정 작업(세션 나누기) | 30분 규칙 세션 ID 만들기 | `source`, `replay_run_id`, 메시지 키(`user_id` 또는 `raw_session_id`), `event_time_utc`, `event_id` |
| Redis 반영 작업 | 세션의 최근 본 상품, 장바구니 수, 사용자 구매 갱신 | `user_id`, `event_type`, `product_id`, `category_id`, `brand`, `price` |
| 구매 전환 예측 입력(Redis 반영 작업이 계산해 예측 요청에 실음) | 세션 안 행동 순서로 확률 계산 | `user_id`, `event_time_utc`, `sequence`, `event_type`, `product_id` |
| Delta 적재·학습 데이터 | 사람 행동과 부하 시험 데이터 빼기, 재생 실행 나누기 | `source`, `replay_run_id` |
| 원본 대조 | 원본 행으로 되짚기 | `source_file`, `source_row` |
| 추천 성과 측정 | 클릭률, 모델 버전별 비교 | `impression_id`, `request_id`, `position`, `rec_model_version`, `is_fallback` |
| 예측 정답 연결 | 세션이 끝난 뒤 실제 구매 붙이기 | `prediction_id`, 예측 기록의 `session_id`, `user_id` |
| 운영 지표 | 반영 지연, 대체 추천 비율 | Kafka 레코드 시각(3장), `produced_at_utc`, `is_fallback` |

원본 데이터의 열 9개(시각, 행동 종류, 상품 ID, 카테고리 ID, 카테고리 이름, 브랜드, 가격, 사용자 ID, 원본 세션 ID)는 모두 행동 토픽 필드에 실린다.
