# 전자상거래 실시간 상품 추천 시스템과 MLOps 파이프라인 기획서

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 실시간 상품 추천과 자동 재학습 MLOps 파이프라인 |
| 대상 | 온라인 종합 쇼핑몰 |
| 작성 팀 | 5팀 (이여찬, 이재원, 김영주, 오재석, 조성현) |

## 1. 추진 배경과 목적

### 1) 추진 배경

| 문제 | 원인 | 영향 조직 |
|---|---|---|
| 사용자가 방금 본 상품이 추천에 반영되지 않음 | 추천 목록을 배치로 미리 계산 | 사용자, 상품·영업 조직 |
| 모델 성능 저하의 늦은 발견과 늦은 교체 | 성능 감시와 재학습을 사람이 수행 | ML·데이터 조직 |
| 쿠폰을 누구에게 줄지 판단할 근거가 없음 | 구매 확률과 무관한 일괄 할인으로 구매 의사가 확실한 사용자에게도 비용 발생 | 마케팅 조직 |

### 2) 추진 목적

1. **사용자 행동의 실시간 추천 반영**
   - 기존 사용자 및 신규 사용자의 행동을 수 초 안에 반영한 추천 상품 최신화
2. **모델 재학습과 교체의 자동화**
   - 정해진 주기, 성능 저하, 데이터 드리프트 발생 시 재학습 및 교체 자동화
3. **구매 확률 기반 쿠폰 대상 선별**
   - 세션별 구매 확률을 행동마다 갱신해 구매 확률이 중간인 세션을 쿠폰 대상으로 선별

**세 목적은 하나의 공통 기반 위에서 구현**

- 실시간 행동 데이터, 학습과 서빙이 함께 쓰는 피처 스토어, 자동 재학습·배포 파이프라인을 한 번 구축해 추천 모델과 구매 전환 예측 모델이 함께 사용
- 수집, 학습, 배포, 감시, 재학습의 자동 연결

### 3) 기대 효과

| 사용자 | 달라지는 점 | 예시 |
|---|---|---|
| 사용자 | 방금 본 상품과 관련된 추천을 즉시 받음 | 무선 이어폰 3개 조회 후 홈·목록으로 가면 관련 상품 추천 |
| 마케팅 담당 | 구매 확률 중간 구간 세션에만 쿠폰 안내 | ① 조회·장바구니 행동마다 구매 확률 갱신<br>② 대상 세션에 쿠폰 1회 표시 |
| ML 운영자 | 모델 교체에 직접 개입하지 않음 | ① 성능 저하 감지 시 자동 재학습<br>② 나은 버전만 교체<br>③ 문제 시 이전 버전으로 복원 |

## 3. 시스템 구성

**8개 영역을 오픈소스로 구성**

- 전체를 클라우드(AWS)에 배포
- 클라우드와 동일한 구성을 팀원 PC 5대의 노트북 클러스터에 두고 개발·시험

| 영역 | 구성 요소 | 역할 |
|---|---|---|
| 실시간 수집·처리 | Kafka, Spark 스트리밍, 로그 재생기 | 행동 이벤트를 실시간 피처로 계산 |
| 피처 스토어 | Redis(온라인), S3의 Delta Lake(오프라인) | 동일한 피처를 서빙용(Redis)과 학습용(Delta Lake)으로 저장 |
| 추천 모델 | 상품 관계표, LightGBM 순위 모델 | 함께 본 상품 후보 추출과 순위 결정 |
| 구매 전환 예측 | 세션 단위 분류 모델 | 세션별 구매 확률 계산과 정답 생성 |
| 재학습·배포 | Airflow, MLflow | 재학습·비교·교체·복원 자동화 |
| 서비스 | Django 화면, FastAPI 추천 API, PostgreSQL | 쇼핑 화면, 추천·쿠폰 제공, 기록 |
| 모니터링 | Prometheus, Grafana | 지연·성능·드리프트 감시와 알림 |
| 배포 인프라 | Kubernetes(k3s) | 클라우드 배포, 노트북 클러스터 개발·시험 |

### 1) 추천 방식

- 최근 30일 행동으로 상품 관계표(상품 기반 협업 필터링)를 만들어 후보 추출
- 장바구니 상품과 최근 관심 상품을 앞에 배치
- 나머지 자리는 순위 모델(LightGBM)이 결정
- 순위 모델이 결정한 순위가 고정 규칙 정렬(장바구니 → 최근 관심 → 구매 인기)보다 낫지 않으면 고정 규칙 정렬로 응답

### 2) 배포 환경

- 클라우드는 시험·발표 기간에만 가동
- 평소 개발과 장시간 재생은 노트북 클러스터에서 수행
- 데이터베이스는 클라우드와 로컬 모두 서로 다른 서버의 주·대기 2대로 복제

## 5. 목표 기준

- ※ 표시는 측정 전 가안
- ※ 표시 값은 1차 측정 뒤 확정
- 추천 목표의 괄호 값은 10월 구매 상위 10개 상품을 11월 1~2주 구매 세션에 적용해 측정한 값
- 구매 전환 예측 목표의 괄호 값은 10월 27~31일 사용자 1% 개발 평가 값

| 영역 | 지표 | 목표 | 검증 방법 |
|---|---|---|---|
| 실시간 반영 | 행동 → 온라인 피처 스토어(Redis) 반영 지연 | p95 5초 이내(로컬) ※ | 구간별 시각을 실제 시계로 측정 |
| 추천 품질 | NDCG@10 | 0.11 이상 ※(인기 상품순 추천 0.10) | 학습에 쓰지 않은 11월 1~2주 구매 세션, 사용자 단위 재표집 |
| 추천 품질 | Recall@10 | 0.20 이상 ※(인기 상품순 추천 0.18) | 학습에 쓰지 않은 11월 1~2주 구매 세션, 사용자 단위 재표집 |
| 구매 전환 예측 | AP(예측 건 기준) | 0.20 이상 ※(장바구니 담기 여부만 보는 단순 규칙 0.15) | 세션 종료로 확정된 실제 구매로 계산 |
| 응답 속도 | ① 추천 API p95<br>② 실패율 | ① 100ms ※<br>② 1% 이하 ※ | 추천·구매 전환 예측·행동 전송 요청을 섞은 부하 시험 |
| 데이터 처리량 | ① 지속 유입<br>② 순간 최대 | ① 초당 약 2,100건 ※<br>② 초당 약 2,400건 ※ | 최대 유입 구간을 재생 배속을 올려 가며 배속마다 10분 이상 재생 |
| 학습·서빙 일치 | 학습 코드와 서빙 코드에 같은 입력을 넣은 계산 결과 | 100% 동일 | 단위 테스트로 두 결과 대조 |
| 학습·서빙 일치 | 온라인·오프라인 피처 스토어 값 대조 | 100% 일치 | 온라인·오프라인 피처 스토어에서 같은 처리 시점의 표본 값을 뽑아 대조 |
| 재실행 정확성 | 이벤트 중복·누락 | 0건 | 이미 처리한 기간을 다시 처리한 뒤 결과 대조 |
| 자동 운영 | 재학습·교체 중 사람 개입 | 0회 | 재학습 주기 안의 전 과정 자동 완료 확인 |
| 자동 운영 | 이전 버전 복원 뒤 API 응답 모델과 복원 대상 버전의 불일치 | 0건 | 교체 직후 복원 실행, API 응답 버전과 모델 레지스트리(MLflow) 표시 대조 |
| 가용성 | 5분 구간 성공 비율 평균 | 클라우드 99%, 로컬 99.9% | 클러스터 외부 요청의 실패·시간 초과 집계 |
| 장애 내성 | 재시작 뒤 데이터 누락·모델 버전 불일치 | 0건 | Kafka·Redis·DB·모델 서빙 강제 재시작 후 복구 완료 시점 전후 대조 |

- 추천 정답은 추천을 받은 세션에서 추천 이후 실제 구매한 상품
- 지속 유입 목표는 원본 로그의 1분 평균 최대치(초당 약 140건)에 재생 배속 10배와 여유 배수 1.5배(가안)를 곱한 값
- 순간 최대 목표는 1초 단위 최대치(243건)에 10배를 곱한 값
- 재생 배속 10배는 11월 한 달 로그를 약 3일(72시간)에 재생해 프로젝트 기간 안에 재생·재학습 시험을 반복하기 위한 값
