# 버전표

기준일: 2026-11-18. 버전은 PyPI, GitHub 릴리스, Maven 저장소, 각 도구의 공식 지원표에서 확인했다. 도구를 고른 이유는 설계 초안에 있다.

이 표가 팀의 기준 버전이다.

- 컨테이너 이미지와 의존성 파일(Dockerfile, requirements 등)은 이 표의 버전으로 고정한다.
- 버전을 바꾸려면 PM 승인을 받고, 이 표와 결정 목록을 먼저 고친다.
- 표에 없는 도구를 새로 쓰려면 이 표에 추가를 요청한다.

### 2.4 Spark·Delta 설정값

버전과 함께 고정할 설정값이다. 근거는 데이터 파이프라인 설계서의 측정(11-19)이다.

| 설정 | 값 | 상태 | 근거 |
|---|---|---|---|
| `spark.databricks.delta.snapshotPartitions` | 1 | 변경(측정 근거, 11-19) | 멱등 쓰기 옵션(`txnAppId`·`txnVersion`)을 쓰면 Delta가 커밋마다 테이블 상태를 다시 계산한다. 기본값 50에서는 로컬 디스크에서도 커밋 한 번이 약 1.6초, 1로 낮추면 약 0.37초였다(옵션 없이는 0.1~0.2초). 샘플 규모의 측정이므로 테이블 파일이 많아지면 다시 잰다 |
| 작은 파일 합치기(OPTIMIZE) 주기 | 측정 뒤 정함(예: 하루 경계마다 일 배치 뒤) | 운영 항목 | 스트리밍 적재는 적재 간격마다 작은 파일을 만든다. 파일이 쌓이면 위 상태 계산과 읽기가 느려진다. 합칠 때는 그 표를 쓰는 작업과 충돌하지 않게 시간을 정한다 |
| Delta 적재 간격(트리거) | 30~60초(측정 뒤 확정) | 제안 | 간격이 길수록 커밋 수와 S3 요청 요금, 작은 파일 수가 준다. 흉내 낸 S3에서 커밋 한 번에 왕복 약 43번분의 지연이 쌓였다(실제 요청 수는 1주 차에 확인). Redis 반영과 분리되어 있어 길게 잡아도 반영 지연에는 영향이 없다 |

## 3. 의존성 해석 결과

`uv pip compile`로 Python 3.12·리눅스(x86_64) 기준 의존성 해석을 돌렸다. 패키지들이 선언한 버전 조건끼리 충돌하지 않는지만 본 것이다. 실제 설치·실행 시험은 아니다.

- 2.1의 파이썬 패키지는 Django 5.2와 함께 해석에 성공했다. Airflow와 LLM 도구는 제외했다.
- 이 과정에서 충돌 두 건을 찾아 버전을 낮췄다. Feast 때문에 `prometheus-client`는 0.24.1로, `redis`는 7.4.1로 낮췄다.
- Airflow는 4장의 제약 파일로 해석에 성공했다.

## 4. Airflow 설치 방법

Airflow는 의존성이 많아 공식 제약 파일(constraints file)과 함께 설치한다. 다른 패키지와 같은 환경에 섞지 않는다.

공식 제약 파일은 Spark 접속용 경량 클라이언트(`pyspark-client`)를 4.3.0으로 고정한다. 그래서 그 줄만 4.2.0으로 바꾼 프로젝트용 제약 파일을 만들어 쓴다.

```bash
curl -sL https://raw.githubusercontent.com/apache/airflow/constraints-3.4.0/constraints-3.12.txt \
  | sed 's/^pyspark-client==4.3.0/pyspark-client==4.2.0/' > constraints-airflow.txt
pip install "apache-airflow[postgres]==3.4.0" apache-airflow-providers-apache-spark==6.3.4 \
  --constraint constraints-airflow.txt
```

Airflow에서 Spark 작업을 돌리는 방식에 따라 추가로 필요한 것이 다르다. 두 방식은 따로 시험한다.

- `spark-submit`으로 제출하는 방식: Airflow 이미지에 Spark 4.2.0 배포판과 Java 21이 있어야 한다. 그 밖에 Spark 접속 설정, 작업용 이미지와 그 안의 파이썬 패키지, Kubernetes 권한이 필요하다.
- Spark Connect로 접속하는 방식: Connect 서버를 따로 띄워야 한다. 또 Feast의 Spark 저장소처럼 Connect에서 막히는 기능이 있다.

## 5. 남은 확인 사항

- 시험 항목: Spark 4.2에서 Feast의 Spark 오프라인 저장소(일반 Spark 세션)와 Soda v4(데이터 계약 방식)가 실제로 도는지 확인한다.
- MLflow의 PostgreSQL 18 백엔드는 연결 시험으로 확인한다.
- S3 위 Delta 표에 여러 Spark 프로그램이 동시에 쓰는 경우는 버전을 맞춘다고 해결되지 않는다. 표마다 쓰는 프로그램을 하나로 두는 규칙을 따른다(데이터 파이프라인 설계서).
- Delta Lake가 Spark 4.3을 지원하는 버전을 내면 Spark를 올릴지 검토한다.
