## 현재 배치와 자원

| 노드 | 공통 서비스 | 서비스 + 시스템 예약량¹ | AWS EC2 | 홈서버 VM 할당량¹ |
|---|---|---:|---|---:|
| 1 | Kubernetes 컨트롤 플레인 | 실측 전 | t3.xlarge | 4 / 8 |
| 2 | Kafka ①, Spark 익스큐터 ①, FastAPI 2개, Prometheus | 5.85 / 19.125 | t3.2xlarge | 8 / 24 |
| 3 | Nginx, Django 2개, Redis, 장바구니 워커 | 3.10 / 13.875 | t3.xlarge | 6 / 22 |
| 4 | Kafka ②, Spark 드라이버, 데이터 재생기, Jenkins 컨트롤러, Argo CD·Rollouts | 5.25 / 22.75 | t3.2xlarge | 8 / 24 |
| 5 | Kafka ③, Spark 익스큐터 ②, Airflow, MLflow, Grafana | 5.25 / 약 19.5 | t3.2xlarge | 8 / 22 |

¹ 숫자 쌍은 **vCPU / GiB** 순서다. 서비스 예약량에는 워커당 시스템 몫 1 vCPU / 2 GiB가 들어간다. 홈서버 VM 할당량은 VMware에서 해당 노드에 줄 전체 용량이다. 아래 전용 DB는 별도로 계산한다.

- **홈서버** — PC당 12코어·16논리 프로세서·32 GiB 기준. Kubernetes VM 5개와 DB VM 3개에 총 37 vCPU / 103 GiB를 배정한다. 호스트용 RAM은 PC 순서대로 22·8·9·8·10 GiB, 합계 57 GiB다.
- **AWS** — 위 노드 5대에 PostgreSQL 전용 `t3.micro` 3대와 관리용 배스천 `t3a.micro` 1대를 더해 총 9대다. 3번은 퍼블릭 웹 진입점이다.
- **웹 배치** — Django는 3번에 고정한다. 표는 평시 FastAPI 2개가 2번에 있는 경우이며, 새 백엔드 Pod는 2·4·5번 중 자리가 있는 노드에 배치한다.

### 서비스별 산정 근거

| 서비스 | 배정량 (vCPU / GiB) | 배치 근거 |
|---|---|---|
| 홈서버 PostgreSQL | VM당 1 / 1 | PC 1에 주 DB와 대기 DB, PC 3에 대기 DB를 둔다. PC 1 장애 시 PC 3에 복제본이 남는다. |
| Kafka | 브로커당 0.5 / 10 | 세 워커에 분산해 한 워커 장애의 영향을 브로커 하나로 제한한다. |
| 실시간 Spark | 드라이버 1 / 1.5, 익스큐터당 1.5 / 3 | 드라이버 1개와 익스큐터 2개로 시작한다. |
| Redis · 재생기 | Redis 1 / 10, 재생기 1 / 5 | Redis는 웹 요청을 처리하는 노드에, 재생기는 데이터 처리 워커에 배치한다. |
| Prometheus · Grafana | Prometheus 0.25 / 1, Grafana 0.75 / 1.5 | 기존 206번의 11월 8~20일 메모리(PSS) 평균·최대는 각각 218.5·365.9 MiB, 883.9·960.6 MiB였다. Grafana는 플러그인을 포함한다. |

홈서버 DB는 내부망에, AWS DB는 공인 IP 없는 프라이빗 서브넷에 두고 앱·복제·관리 경로에서만 접근하도록 계획한다.

## 동시 실행 조건

Jenkins가 테스트한 이미지의 digest를 배포 저장소에 기록하면 Argo CD가 변경을 적용하고 Argo Rollouts가 카나리를 진행한다. 프론트·백엔드 모두 `maxSurge: 1`, `maxUnavailable: 0`을 기준으로 추가 Pod 한 개의 자리를 확보한다.

| 상황 | 필요한 자원 (vCPU / GiB) | 운영 방법과 남는 자원 |
|---|---|---|
| 프론트 카나리 | 사이드카 포함 추가 0.30 / 0.5625 | 3번에 배치. AWS는 0.60 / 1.5625, 홈서버는 2.60 / 7.5625가 남는다. |
| 백엔드 카나리 | 사이드카 포함 추가 1.30 / 1.5625 | 5번에 배치한 경우 AWS는 1.45 / 약 10.94, 홈서버는 1.45 / 약 0.94가 남는다. |
| 홈 4번 재생 + 빌드 | 합계 7.25 / **26.75** | VM 메모리 **24 GiB**를 초과한다. 재생기를 내린 뒤 빌드하거나 빌드 에이전트를 3번에 둔다. 후자의 경우 프론트 카나리까지 포함한 3번 사용량은 5.40 / 18.4375다. |
| AWS 4번 재생 + 빌드 | 빌드 에이전트 추가 2 / 4 | 같은 노드에서 동시 실행할 수 있는 계획이다. 계산상 0.75 / 5.25가 남는다. |

## 검증 상태

현재 배정값은 배포 전 산술 검토 결과다. 실제 환경에서 확인할 항목은 다음과 같다.

- **배포·복구** — 노드의 할당 가능 자원과 Pod 요청량 대조, 카나리 전환·롤백, PC 1 장애 후 DB 자동 승격과 쓰기 재개.
- **처리 성능** — 같은 입력을 초당 15건과 150건으로 재생해 Kafka 적체, Spark 처리율·배치 시간, 익스큐터 CPU·메모리, 재생 후 적체 해소 시간을 측정한다. 적체가 지속되면 원인을 확인하고 증설 여부를 결정한다.
- **동시 부하** — 일 배치와 실시간 처리의 동시 실행, 새 수집 대상과 대시보드 부하에서의 모니터링 Pod 메모리를 확인한다.

### 이전 AWS Spark 자원 배치 계획

EC2는 Kubernetes 5대(1·3번 t3.xlarge, 2·4·5번 t3.2xlarge), PostgreSQL 3대(t3.micro), 퍼블릭 배스천 1대(t3a.micro, 2 vCPU·1 GiB)로 구성한다. 총 9대, 40 vCPU·132 GiB다.

실시간 처리 작업을 Spark 애플리케이션 하나로 묶는다. 드라이버 1개에 1.5 vCPU·3 GiB, 익스큐터 2개에 각각 2.5 vCPU·6 GiB를 배정한다. 상시 Spark 합계는 6.5 vCPU·15 GiB다. 메모리는 Pod 단위 총예산이며 Spark 힙과 오버헤드를 포함한다.

| 노드 | Spark 배치 | 기타 서비스 및 시스템 몫을 반영한 CPU 여유 | RAM 여유 |
|---|---|---:|---:|
| 1번 컨트롤 플레인 | 앱 배정 없음 | 앱 예산 0 | 앱 예산 0 |
| 2번 프라이빗 | 익스큐터 1개 | 1.15 vCPU | 6.875 GiB |
| 3번 퍼블릭 · t3.xlarge | Spark 배정 없음 | 0.40 vCPU | 1.125 GiB |
| 4번 프라이빗 · t3.2xlarge | 드라이버 1개 | 3.40 vCPU | 9.75 GiB |
| 5번 프라이빗 | 익스큐터 1개 | 1.75 vCPU | 5.5 GiB |
| 프라이빗 워커 합계 | 드라이버 1개·익스큐터 2개 | 6.30 vCPU | 22.125 GiB |

2·4·5번 프라이빗 워커에는 Kafka 브로커를 하나씩 배치한다. 브로커당 배정량은 0.5 vCPU·13 GiB이며, 세 브로커의 합계는 1.5 vCPU·39 GiB다. 표는 이 배정량과 시스템 예약을 반영한 계획값이다. 3번은 데이터 재생기와 Redis를 포함해 서비스에 2.60 vCPU·12.875 GiB, 시스템에 1 vCPU·2 GiB를 배정한다. 워커 4대의 전체 여유는 6.70 vCPU·23.25 GiB다. 드라이버를 재시작하면 같은 앱에 묶인 실시간 처리도 함께 재시작된다.

### Jenkins CI, Argo CD 동기화와 Argo Rollouts 카나리 배포

4번 워커에서 Jenkins가 커밋을 체크아웃해 테스트하고, 성공하면 컨테이너 이미지를 빌드해 레지스트리에 푸시한다. 레지스트리 종류와 주소는 미정이다. 푸시가 성공하면 Jenkins가 배포용 Git 저장소의 웹/API Rollout 매니페스트에 새 이미지 digest를 커밋한다. 4번의 Argo CD는 자동 동기화로 그 변경을 클러스터에 적용한다. Argo Rollouts 컨트롤러가 새 ReplicaSet을 만들고 카나리 단계를 진행한다. Django 프론트 Pod는 3번 퍼블릭 워커에 고정한다. FastAPI 백엔드 Pod는 2·4·5번 프라이빗 워커 중 요청량을 수용할 수 있는 노드에 스케줄링한다. 노드별 잔여량 표는 평소 FastAPI 2개가 2번에 있는 배치 예시로 계산했다. 카나리에서 새 Pod 1개를 추가하는 경우, 사이드카 포함 프론트 요청량 0.30 vCPU·0.5625 GiB는 3번에 들어가고, 백엔드 요청량 1.30 vCPU·1.5625 GiB는 현재 평시 예산에서 4번 또는 5번에 들어간다. 실제 배치 노드에 따라 배포 후 잔여량이 달라진다.

| 4번 구성 | CPU 예산 | RAM 예산 | 실행 시점 |
|---|---:|---:|---|
| Jenkins 컨트롤러 | 0.50 vCPU | 2 GiB | 상시 |
| Argo CD 전체 | 1.00 vCPU | 2 GiB | 상시, 소규모 비고가용성 구성의 초기 추정 합계 |
| Argo Rollouts 컨트롤러 | 0.10 vCPU | 0.25 GiB | 상시, 초기 추정 |
| Jenkins 빌드 에이전트 | 2 vCPU | 4 GiB | 빌드 시 1개 |

상단 노드 표는 Jenkins·Argo CD·Argo Rollouts의 상시 자원을 포함한 평시 기준이다. 빌드 중 4번의 여유는 1.40 vCPU·5.75 GiB다. 빌드 캐시와 작업 공간용 디스크는 50 GB를 초기 예산으로 잡는다. 카나리 배포 때 잠시 늘어나는 웹/API Pod와 사이드카의 자원은 해당 서비스 노드에서 별도로 확보한다.

### 일 배치

일 배치는 별도 예약 Spark 앱으로 실행한다. 일 배치 최소 추정량은 앱 전체 4 vCPU다. 실시간 앱이 실행 중이고 CI 빌드가 없을 때 프라이빗 워커 합계 여유는 6.30 vCPU·22.125 GiB, 4번 단독 여유는 3.40 vCPU·9.75 GiB다. 일 배치 하단 추정치 4 vCPU·8 GiB 전체를 4번에 두려면 CPU 0.60 vCPU를 더 확보해야 한다. 예시로 배치 드라이버(1 vCPU·2 GiB)는 5번에, 익스큐터(3 vCPU·6 GiB)는 4번에 두면 현재 예산에 들어간다. 상단 추정치 8 vCPU는 프라이빗 전체 여유를 초과한다. 실행 시간과 실제 소요 자원은 미확정이다.

### 기존 부하 시험의 증설 가정

일 배치와 CI 빌드가 실행되지 않는 동안에는 4번에 세 번째 익스큐터(2.5 vCPU·6 GiB)를 추가할 공간이 있다. 추가 시 4번 여유는 0.90 vCPU·3.75 GiB이므로 일 배치 동시 실행 예산을 다시 확인한다.

상태는 배포 전 계획이며 부하 시험 결과는 미측정이다.
