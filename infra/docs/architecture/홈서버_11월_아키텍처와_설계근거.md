# 쇼핑·추천 인프라 | 홈서버에서 AWS까지

쇼핑·추천 인프라는 2026년 11월 26일의 배치 계획과 예산 가정을 기준으로 작성했다. 부록에는 설계에 참고한 기존 게임·광고 인프라의 11월 운영 점검 기록을 정리했다.

## 1. 홈서버를 선택한 이유

기존 PC와 공유 저장소를 활용하면 추가 클라우드 지출 없이 웹과 실시간 처리를 운영할 수 있다. 전력과 디스크 비용은 별도다. 시험 환경은 Windows와 VMware를 사용하며, 운영 시에는 가상화 부담을 줄이는 컨테이너 중심 구성을 지향한다.

Kafka가 이벤트를 보관하므로 Spark 처리가 늦어져도 보존 기간 안에 밀린 입력을 다시 읽을 수 있다. Redis에 최신 상태를 두어 웹 요청에 응답하고, Delta 이력은 품질 검사와 재처리에 사용한다. 실시간 작업을 한 앱으로 묶어 상시 자원을 줄이는 대신 드라이버가 재시작되면 해당 앱의 처리도 함께 멈춘다.

외부 접속은 강의장 회선에 의존한다. Cloudflare 경로 지연이 시연에 영향을 주면 서울 EC2의 Nginx를 대체 진입점으로 검토한다. PC 1이 멈추면 주 DB와 단일 컨트롤 플레인이 함께 중단된다. 다른 PC의 복제본으로 쓰기를 재개할 수 있는지는 장애 시험이 필요하다. [홈서버 배치도](../../README.md#1-홈서버) · [노드별 배치와 장애 검증 항목](cost/AWS·홈서버_Kubernetes_비용_계산.md)

## 2. 하이브리드에서 일 마감을 AWS로 옮기는 이유

마감 작업은 재생한 데이터의 날짜를 기준으로 실행한다. 홈서버가 웹 요청을 받는 동안 서울 리전의 일시적인 워커에서 품질 검사, 누락 구간 재처리, 최근 7일 인기 상품 집계를 순차 실행하면 홈서버에 배치용 최대 자원을 상시 확보할 필요가 줄어든다. 예산은 `m6i.xlarge` 한 대를 기준으로 잡았다. Jenkins 빌드는 홈서버에서 실행한다. Airflow로 주기를 관리하는 모델 재학습은 AWS 이관 후보이며, 재학습 시간은 일 마감 견적과 별도다. [하이브리드 배치도](../../README.md#2-홈서버-중심-하이브리드) · [홈서버 워커 배치와 빌드 조건](cost/AWS·홈서버_Kubernetes_비용_계산.md)

**예산 산식.** 홈서버 중심 견적은 하루치를 10배속으로 144분간 재생한 뒤 AWS에서 20분간 마감하는 가정이다. 30회면 EC2 가동은 10시간이다. 당시 단가와 환율로 EC2·공인 IPv4 가동료는 회당 약 118원, 30회 약 3,552원이다. EBS·S3까지 포함한 당시 추정은 70시간·25회에 12,380~19,322원, 105시간 일정·30회에 13,111~20,750원이다. 20분은 AWS 실측 전 가정이다. 전체 예산은 300달러 × 1,340원 = 402,000원으로 정정했다. ## 3. AWS 전체 배포의 운영 조건

웹과 데이터 처리를 AWS에 두면 강의장 회선이 끊겨도 외부 사용자의 요청 경로가 유지된다. 다섯 계정에 자원을 나누고, 관리자는 배스천을 통해 접근하며 DB에는 공인 IP를 할당하지 않는다. 클러스터에서는 Kafka와 Spark가 함께 동작하는 워커에 더 큰 인스턴스를 배정한다.

비용은 70시간과 105시간 가동 일정을 기준으로 비교했다. 테스트 중에는 스팟 워커 0·1·2대를 비교하고, 시연 14시간은 인스턴스 회수에 따른 중단 위험을 줄이기 위해 온디맨드로 산정했다. [AWS 전체 배치도](../../README.md#3-aws-전체-배포) · [EC2 사양과 워커별 자원 예산](cost/AWS·홈서버_Kubernetes_비용_계산.md)

## 4. 팀 GitHub 목표 구조 · AWS에서 웹·추천 제공

| 서비스 경로 | 배치와 역할 |
|---|---|
| 사용자 → AWS NLB → AWS Kubernetes | Django·FastAPI가 웹·추천 요청을 받고 AWS의 Kafka·Spark·Redis가 행동 판정과 최신 추천 상태를 처리한다. |
| AWS Kafka → 노트북 | 노트북이 이벤트를 읽어 Delta 이력을 저장하고 일 배치·재학습을 수행한다. PostgreSQL은 PC 4에 주 DB, PC 3·5에 대기 DB를 둔다. |
| 강의장 회선 장애 | AWS에 있는 비로그인 쇼핑·인기 상품 대체 추천을 계속 제공하는 것이 목표다. 홈 DB에 의존하는 로그인과 재생은 영향을 받는다. |

2절의 예산안에서는 회선이 끊기면 외부 사용자가 홈서버의 웹에 접근할 수 없다. 팀 구조도에서는 이 조건을 고려해 사용자 요청 경로를 AWS에 배치했고, 행동 판정과 Redis 반영을 각각 별도 Spark 앱으로 잡았다.

**보고서에서 확정할 조건.** 11월 26일 기준 팀 요구사항은 요청 처리를 AWS에 두며 비용 요건은 30만 원이었다. 강의장 회선 단절 시에도 비로그인 서비스를 제공해야 한다면 팀 구조를 기준으로 AWS 상시 워커·NLB·스토리지·전송 비용을 다시 산정해야 한다. 위의 일 마감 견적을 그 구조에 적용할 수 없다. ## 부록. 설계에 참고한 기존 게임·광고 인프라 운영 기록

11월 11일 점검 기준 홈서버는 Windows·WSL 기반 8대였다. 199·200은 게임 서비스, 201~203은 PostgreSQL·Kafka 클러스터, 204는 광고 백엔드, 206은 Prometheus·Grafana·알림을 맡았다. 205는 SSH와 모니터링이 확인됐고 포인트 동기화는 계획 단계였다. AWS 8대의 역할은 게임 Nginx, 광고 프론트, 배스천, Manager API, Kubernetes 제어 노드와 워커 3대였다. AWS 웹 진입점에서 WireGuard를 거쳐 홈서비스에 접근했고 AWS Spark는 배스천 TCP 중계와 터널을 거쳐 홈 Kafka를 읽었다.

| 운영 경험 | 실제 조치와 설계에 참고할 근거 |
|---|---|
| 업무 쓰기와 분석 처리의 속도가 다름 | 게임·광고 DB Outbox → Debezium CDC → Kafka → AWS Spark → S3 Bronze → Silver·광고 Gold로 처리했다. 당시 Kafka 보존은 7일이었고 Bronze는 체크포인트에서 재개했다. 재시작 시 유실 여부는 보존 기간·디스크 여유·대사 결과까지 확인해야 한다. |
| 단순 재시도만으로 야간 중단을 견디기 어려움 | Bronze 앱 2개의 재시도 횟수가 소진되는 문제를 보고 재시작 정책을 Always로 바꿨다. S3 원본·체크포인트 기록, 대사용 manifest 작성·조회, 지연 감시 권한을 역할별로 나눴다. 체크포인트가 전진해도 원본과 고유 이벤트 수가 일치하는지는 별도 검증이다. |
| Windows는 켜져 있지만 WSL이 멈춘 사례 | 부팅 시 WSL을 실행하고 1분마다 재기동을 시도하며 WSL 안에서 sleep infinity로 배포판을 유지했다. 주요 서비스는 systemd로 자동 시작했다. 199·200·205에서 예약 작업 종료 후 38~55초 내 재실행을 확인했다. 업무 전체 복구 시간은 미집계다. |
| WSL 주소 변경과 Windows 포트 전달 장애 | 201~206의 내부 IP 변경에 맞춰 포트 프록시를 갱신했다. 사용 경로 38개를 갱신 대상으로 관리하고 201~203에 IP Helper 덤프·재연결 감시를 붙였다. 당시 IP Helper 충돌의 근본 원인은 미해결이었다. |
| 공유기의 DHCP 예약과 관리 권한 제약 | 서버 주소를 수동 고정해 서비스 경로를 유지했다. 높은 주소를 쓰더라도 DHCP 중복 할당 가능성은 남는다. 관리 접근은 개인별 키와 지정 출발지·목적지 포트로 제한했다. 당시 연결 시험은 허용 131건, 차단 55건이 예상과 일치했다. |
| 운영 성과의 측정 범위 | 11월 11일 점검 시 DB 복제 지연 0, CDC 2개 실행, 모니터링 대상 25개 정상으로 기록했다. 이후 모니터링 중지와 자동 시작 해제 요청도 있었다. 이전 환경의 특정 시점 결과로만 인용할 수 있다. |
